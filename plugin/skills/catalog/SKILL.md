# Catalog — каталог решений сервиса

Собери `catalog.md` в корне целевого проекта: **что уже есть и из чего собрано**, одной строкой на
единицу. Код первичен — каталог указывает на него, не пересказывает. Формат и правила —
`../../resources/catalog/catalog-format.md`, пример — `../../resources/catalog/catalog.example.md`.

Принцип: **извлекаем всё, квалифицируем то, что иначе переизобретут.** Извлечение дешёвое и
детерминированное (скрипт), квалификация — фраза «что это / для какой задачи» по коду.

## Когда применять

- В проекте нет `catalog.md`, предстоит сборка нескольких страниц (или пользователь просит индекс).
- Репо изменился, каталог устарел — режим обновления.
- Проект не на Next.js pages-router — скрипт не поможет, каталог собирается по формату вручную
  (разделы те же; начинать с архетипов страниц и источников данных).

## Как вести

1. **Прочитай формат** (`catalog-format.md`): разделы, вид строки, правила («формулировки — цель или
   факт, не способ», «грабли — факт», «запись — в том дереве, где код», «не индексировать всё»).
2. **Извлеки кандидатов скриптом:**
   `node ../../resources/catalog/extract-catalog.mjs <repoRoot> --out <repoRoot>/catalog.md`
   (путь скрипта — относительно папки этого скилла). Скрипт группирует страницы по главному
   компоненту в архетипы, находит кастомные блоки page-constructor, компоненты и обёртки, модели
   контента, серверные методы и признаки конвенций, считает, сколько страниц использует единицу, и
   раскладывает: **основной список** (архетипы с реальными страницами · кастомные блоки · конвенции ·
   компоненты, которые используют ≥ 3 страниц · внешние источники, которые кто-то использует) и
   **«Остальное»** свёрнутыми кандидатами.
3. **Квалифицируй основной список по коду:** замени заготовки «уточнить: что это / для какой
   задачи» на одну фразу-задачу; у источников данных — ограничения (кэш, токен, покрытие); у
   конвенций — правило одной фразой + пример-файл. Назначение страницы не читается из кода
   (внутренний стенд, превью для эмбедов) — **спроси владельца**, не догадывайся; в один вопрос
   собирай несколько единиц.
4. **Разведка «что переизобретут» (рекомендовано):** посмотри 2–3 последних PR с новыми страницами
   или отчёт последней сборки — что там сделали заново при наличии похожего в репо, поднимай в
   основной список и запиши граблей причину.
5. **Грабли** — только реально прожитые (из отчётов сборок, фидбэка, PR); фактом, не рецептом.
   Нет прожитых — строка без граблей, это нормально.
6. **Раздел «Вне каталога, но существует»** — legacy, внутренние стенды, разделы со своей механикой:
   одна строка с причиной, чтобы следующий исполнитель не переоткрывал.
7. **Покажи итог** владельцу: сколько единиц по разделам, сколько в «Остальном», какие вопросы
   остались. Файл — `catalog.md` в корне проекта (туда смотрит `create`).

## Режим обновления (репо изменился)

Повторить шаг 2 в отдельный файл (`--out /tmp/catalog.new.md`) → сравнить с текущим: новые
кандидаты — добавить в «Остальное» или квалифицировать; единицы, чей код исчез, — пометить
«удалено» или перенести в «Вне каталога» с причиной. Фразы, грабли и ручные правки владельца
не перезаписывать.

## Чего не делать

- Не писать рецепты вместо фактов и не превращать строку в абзац — подробные описания читаются
  буквально и толкают к неподходящему переиспользованию.
- Не индексировать всё подряд: 40–60 строк на сайт среднего размера — норма, 150 — нет.
- Не квалифицировать назначение страниц догадкой — вопрос владельцу дешевле ошибочной строки.

## Связь

- Каталог читает `create` (перед новой страницей) и пополняет `write-back` (после сборки).
- Сиблинг `synthesize-profile` описывает **вкус** сервиса (тема, плотность, конвенции формы);
  каталог — **что собрано** и из чего. Это разные файлы с разным ритмом изменений.
