# gravity-build

Собирай UI на **настоящих** компонентах Gravity UI «как принято», а не по памяти. Источник правды про
Гравити — бандл-registry рядом с этим скиллом; per-service вкус — опциональный профиль из целевого
проекта.

## Когда применять

- Запрос собрать / сверстать прототип, приложение, экран, страницу, компонент на **Gravity UI /
  Гравити** (лендинг, дашборд, форма, настройки, список, таблица…).
- **Доработка существующей сборки на Gravity UI** — любая правка уже собранного (колонка в
  таблице, поле в форме, тема, состояния): в проекте есть `@gravity-ui/*`-зависимости,
  `scenarios.manifest.json` или `service-profile.json`. Вход — через блок вопросов
  (brownfield-recap), даже если правка кажется мелкой.
- **Дана ссылка на Figma-макет** (файл/фрейм, node-id) — перенос макета в живой прототип на
  Gravity-компонентах. Требуется доступ к Figma (MCP-инструменты в среде); чтение макета добавляет
  к обычной цене сборки заметный объём работы (макет читается по секциям).
- Любая сборка React + TypeScript, где дизайн-система — Gravity UI.

## Порядок работы

1. **Открой knowledge-registry и следуй ему.** Entry-point — `../../resources/registry/registry.json`
   (роутер; путь — относительно папки этого скилла, общий ресурс плагина); прочти его первым и работай строго по полю `workflow`: scaffold → pattern →
   interface-foundations → recipe → gravity-foundations → библиотеки (routing / версии — в роутере).
   **Вход — Figma-макет?** Его ведёт шаг 0 workflow: сначала `../../resources/registry/guides/figma-mapping.md`
   (протокол чтения канала по секциям, карта имён кита → код, политика фиделити «макет = что,
   registry = как», обязательный конфликт-отчёт).
   Имена компонентов и пропы сверяй с гайдами (`../../resources/registry/guides/library-uikit.md` и др.) **перед**
   импортом — не подставляй из памяти других дизайн-систем.
2. **Проверь профиль сервиса.** Поищи в корне целевого проекта `service-profile.json` (или
   `.gravity/service-profile.json`):
   - **Есть** → это per-service слой «как принято у нас» (тема/бренд, плотность, раскладка,
     форм-политика, сабсет компонентов, архетипы, словарь). Примени его ручки поверх дефолтов по
     разделу **«Профиль сервиса (если передан)»** в `../../resources/registry/AGENTS.md`: профиль уточняет открытые
     ручки, **не отменяет** корректность registry, омиссия = дефолт.
   - **Нет** → собирай по универсальным дефолтам (baseline).
   **Каталог решений.** Рядом с профилем поищи `catalog.md` (что в проекте уже собрано и из чего:
   страницы по устройству, блоки, компоненты, источники данных, «как принято», грабли; формат —
   `../../resources/catalog/catalog-format.md`). **Есть** → перед новой страницей сверься с ним: что
   уже есть и как устроено; не изобретай новое без необходимости; если существующее не подходит —
   скажи почему (в отчёте сборки, шаг 6). Грабли выбранных единиц прочти до кода. **Нет**, а
   собирать предстоит несколько страниц — предложи завести (сиблинг-скилл `catalog`), не блокируя
   сборку.
3. **Вопросы перед сборкой — одним вызовом `AskUserQuestion`** (инструмент умеет до 4 вопросов
   за раз; выбор с клавиатуры, не текстом; единственное исключение из «одного вызова» — неясный
   интент, он идёт первым отдельно, остальные вопросы — вторым). Задавай только применимые И
   неотвеченные: ответ уже
   прозвучал в брифе, профиле или входе (Figma-макет = источник и интента, и стилей) — вопрос
   снят. Профиль может нести **рекомендуемый выбор** сессионной оси (строка `conventions`,
   осаждается write-back'ом) — такой вопрос всё равно задавай, но рекомендуемой опцией ставь
   профильную. Инструмента `AskUserQuestion` в среде нет, но пользователь на связи — задай те же
   вопросы обычным текстом нумерованными вариантами; спросить некого (автономный /
   headless-прогон) — действуют дефолты, помеченные ★ (профильная рекомендация, если есть,
   побеждает ★-дефолт).
   Каждый заданный вопрос и выбранный ответ зафиксируй в отчёте сборки (материал для write-back).
   - **Интент** — только при неоднозначном брифе (редкий случай: обычно ясно из запроса).
     Неясен — спроси ПЕРВЫМ, отдельным вызовом (от ответа зависит применимость остальных):
     header «Задача»; опции: «Новая сборка с нуля» / «Доработка существующего кода» /
     «Перенос макета из Figma» / «Рестайл: тема и бренд».
   - **Панель прототипа** — если сборка получит сценарный манифест (у паттерна есть контракт
     состояний): header «Панель»; опции: «С панелью (рекомендуется) ★» — *листать состояния и
     тему сможет любой смотрящий, прямо в углу прототипа; в прод-сборку панель не попадает — как
     и сами состояния* / «Без панели» — *состояния переключаются только адресной строкой,
     `?scenario=`*. Канон панели — `scaffold-app-shell` «Прото-панель».
   - **Стили** — если тема не определена (профиль без темы, вход не Figma-макет, бриф молчит):
     header «Стиль»; опции: «Тема Gravity (рекомендуется) ★» — *дефолтная тема системы, сменить
     можно позже* / «Есть бренд-цвет или тема — приложу» / «Стили в Figma-файле — дам ссылку».
     Ответы 2–3 → follow-up свободным текстом (значения / ссылка); бренд-цвет веди Themer-путём
     (`gravity-foundations-theming`), стили из Figma — semantic-оверлеем (`figma-mapping`).
     Синтез стиля из произвольного сайта пока не канон — не обещай.
   - **Самопроверка** — если бриф не решил («быстро / без проверки» в брифе = выбор «без
     проверки»): header «Проверка»; опции: «Полная (рекомендуется) ★» — *по исходникам и в
     браузере: контраст, прокрутка, обход всех состояний + свежий взгляд по скриншотам; нужен Playwright — пакет ставится в
     проект, браузер ~130 МБ — один раз на машину (кэш общий: уже есть от прошлых сборок →
     доставится только лёгкий пакет, скажи об этом честно)* /
     «Только статическая» — *по исходникам, без браузера — быстрее, но итог честно помечается
     частичным* /
     «Без проверки» — *сборка не проверяется, в итоге будет явная пометка об этом*. Пользователь
     ввёл через «Other» название другого браузерного инструмента — браузерную часть проверки
     сделай им best-effort, статические проверки прогони всё равно и пометь в отчёте, какие
     браузерные проверки названный инструмент не покрыл.
   - **Brownfield-recap** — вместо повторного анкетирования: при доработке существующей сборки
     оси, уже материализованные в коде (панель есть/нет, тема подключена, манифест сценариев
     лежит), не переспрашивай вопросами выше — подтверди одним recap-вопросом: в **question**
     перечисли увиденное («В проекте: панель есть, тема meridian, сценариев 5 — оставляю?»),
     header «Как сейчас», опции «Оставить как есть (рекомендуется) ★» / «Поменять — скажу что»
     (ответ → follow-up свободным текстом). Код — источник правды о прошлых выборах, отдельного
     файла-памяти не заводи. Оси, которых в коде нет и бриф молчит, — обычными вопросами в том
     же вызове. Два частных случая: **запрошенная доработка уже материализована в коде** — не
     дублируй: в интерактиве скажи об этом прямо в recap-вопросе, автономно — no-op с явной
     строкой в отчёте; **профильная рекомендация противоречит коду** (профиль советует X, в коде
     Y) — код побеждает как факт прошлого выбора, молча не перестраивай — предложи выравнивание
     в «Что дальше».
4. **Собери** запрошенное как готовый к запуску React + TypeScript проект; версии пакетов — verbatim
   из роутера (`libraries[]` / `bundles[]`), route-only либы ставь целым bundle.
5. **Самопроверка — после зелёного `tsc`/`build`, в режиме, выбранном вопросом шага 3.** Выполни
   сиблинг-скилл **`verify`** в режиме «после сборки»: инструкция — `../verify/SKILL.md`, механика —
   `../verify/harness/HARNESS.md`. Кратко: сборка с живыми сценариями (`VITE_SCENARIOS=1`),
   предпросмотр на временном порту, `run-gate.mjs`, разбор `verdict.json`, свежий взгляд по
   скриншотам (шаг 5 verify); находки чини **классами
   по гайдам registry** (не заплатками под чек), максимум 2 итерации на находку — остаток честно
   опиши. Выбор «Полная» = согласие на установку Playwright/Chromium, если их нет; установка не
   удалась — гейт честно деградирует в static-only (вердикт ЧАСТИЧНЫЙ — скажи об этом).
   **В автономном прогоне ничего не устанавливай** (согласие может дать только живой
   пользователь): Playwright отсутствует → сразу честный static-only. Выбор
   «Только статическая» — сразу static-only с тем же честным вердиктом. Выбор «Без проверки» —
   шаг пропусти, но в отчёте ЯВНО пометь: «самопроверка пропущена по выбору пользователя — сборка
   не проверялась». Финальный предпросмотр оставь работающим на порту пользователя
   (дефолт-порт занят — возьми ближайший свободный) и явно назови URL.
6. **Финал отчёта — языком пользователя, два блока.** Отчёт читает пользователь продукта, не
   мейнтейнер плагина. Без внутренних терминов (гейт / static-only / brownfield / recap — говори
   «самопроверка», «проверка по исходникам», «доработка существующей сборки», «подтверждение „как
   сейчас“»). Изменения описывай тем, что человек увидит на экране, а не хроникой правок. Итог
   проверки — одна-две строки: что проверялось, чем кончилось, где детали (`gate-out/AUDIT.md`); при нуле
   находок линии проверки не перечисляй. Свои промежуточные регрессии, починки по дороге и прочую
   диагностику не выгружай — она доступна по запросу.
   - **Применённые настройки** — каждая с провенансом: «панель: да (вопрос) · тема: meridian
     (профиль) · проверка: полная (дефолт)». Молчаливых решений в отчёте не остаётся; любое
     меняется следующей репликой — сборка инкрементальна.
   - **Из чего собрано** (если в проекте есть `catalog.md`) — короткой таблицей: страница → что
     взято из каталога → что рассмотрено и не подошло, почему → что новое. Это вход для
     `write-back` (пополнение каталога); без каталога блок не нужен.
   - **Что дальше** — предложения, выведенные из отклонённых опций и известных хвостов: отказ от
     панели → «могу добавить позже»; пропущенный или статический гейт → «могу прогнать полный со
     скриншотами»; разделы на демо-данных, состояния вне манифеста — назови. Предлагай, не
     навязывай, сделанного не повторяй.
     Наблюдения свежего взгляда (при полной проверке) — подсекцией здесь же, НЕ отдельным блоком:
     рамка первой строкой — «это не ошибки, сборка рабочая — вот что бросилось в глаза»; 3–5
     пунктов, каждый — ОДНО предложение «что не так» + в скобках дизайн-причина в 2–5 слов
     (формат, образец и запреты — verify, шаг 6; подробности — в `gate-out/AUDIT.md`); починку
     по пунктам не расписывать — одна строка на весь список «могу применить любой — скажи
     номера»; хвост — «ещё N помельче — скажи, покажу»; реакция — номером («сделай 1 и 3»),
     молчание = оставить как есть, не дожимай. Починенное по замеру сюда не входит — оно среди правок выше, без диагностики.
     Ответ «так задумано» зафиксируй в отчёте — материал для write-back (повторный отказ
     осаждается в профиль, наблюдение гаснет).

## Чего не делать

- Не выдумывать компоненты/пропы и не брать «похожие» из других библиотек — всё сверять с registry.
- Профиль **не переопределяет** корректность/идиому (имена, версии, app-shell, «FormRow вместо
  инлайн-`label=`»). При конфликте побеждает registry — пометь комментарием.
- Не подгонять код под гейт-чек и не редактировать файлы `../verify/harness/` — находки чинятся по
  гайдам; подозрение, что гейт ошибается, — опиши пользователю, не «чини» здоровый код.
- Канон скаффолда — Vite. Бриф или целевой проект требуют другой фреймворк (Next.js / Remix) —
  честно скажи, что выверенного канона под него пока нет, и согласуй путь с пользователем; молча
  подменить на Vite или импровизировать чужой scaffold без registry нельзя.
- Static-only-вердикт не выдавать за полную проверку (browser-линии в нём пропущены).

## Структура бандла (читать on-demand)

Registry — общий ресурс плагина, одна копия для всех скиллов (пути — от папки этого скилла):

- `../../resources/registry/registry.json` — **роутер и entry-point** (workflow + libraries / версии +
  routing + patterns + recipes + foundations + scaffold). **Начни здесь.**
- `../../resources/registry/guides/*.md` — вся проза: library-каталоги, recipes, patterns, foundations
  (факт живёт в одном guide).
- `../../resources/registry/AGENTS.md` — тонкий companion: применение профиля сервиса + fallback при
  заблокированном фетче.
- `../../resources/catalog/catalog-format.md` — формат каталога решений сервиса (`catalog.md` в
  целевом проекте): что читать перед новой страницей и что дописывать после.
