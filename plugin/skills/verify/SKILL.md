# gravity-build: verify — проверка сборки гейтом

Headless-проверка Gravity-прототипа по инвариантам качества + обход всех заявленных состояний.
Операционная механика (команды, режимы полный/облегчённый, чтение вердикта) — **`harness/HARNESS.md`**
(рядом с этим SKILL.md); там же дисциплина «чини классами по гайдам, максимум 2 итерации».

## Два режима — определи по контексту вызова

- **«После сборки»** (шаг самопроверки из скилла `create`, либо пользователь просит «собери и проверь»):
  находки гейта **чини сам** — классами по гайдам registry (общий ресурс плагина:
  `../../resources/registry/guides/`), затем re-gate;
  что не сошлось за 2 итерации — честно в отчёт.
- **«Standalone-аудит»** (пользователь навёл на СУЩЕСТВУЮЩИЙ проект: «проверь мой прототип»):
  **по умолчанию — отчёт, НЕ фиксы** (это чужой код). Вердикт → человекочитаемый разбор: что найдено,
  почему это дефект (ссылкой на канон registry), как чинить — рекомендацией. Правки — только по явной
  просьбе пользователя.

## Порядок работы

1. Определи корень проверяемого проекта (package.json). Есть `scenarios.manifest.json` → гейт обойдёт
   все состояния; нет — одиночный аудит начального экрана (тоже валидно).
2. Сборка для гейта: `VITE_SCENARIOS=1 npm run build` (переключатель состояний должен быть живым;
   без него гейт честно скажет «сценарии noop»). Предпросмотр — на ВРЕМЕННОМ свободном порту.
3. `node <этот-скилл>/harness/run-gate.mjs http://localhost:<порт> <проект> <проект>/gate-out` —
   дальше по `harness/HARNESS.md` (полный режим при наличии Playwright; иначе честный static-only).
4. Разбери `verdict.json` по трём признакам (`harness/HARNESS.md` «Как читать вердикт»): `valid` —
   проверка состоялась (нет → причина в `invalid_reason`, отчёт «проверка не состоялась», не «чисто»);
   `complete` + `coverage` — что проверено в каком состоянии, что пропущено; `summary` — находки,
   агрегат по всем состояниям. В static-only скриншотов не бывает — не ищи и не обещай их.
5. **Свежий взгляд по скриншотам** (только полный режим — есть `gate-out/full*.png`). Гейт меряет
   известные классы дефектов; скриншоты дополнительно смотрятся глазами на предмет неизвестных.
   Смотреть должен НЕ автор сборки: запусти суб-агента (штатный инструмент запуска агентов;
   ОДНОГО на все скриншоты — дефолт + сценарные; модель не занижай — качество взгляда растёт с
   моделью), дай ему только пути скриншотов и одну строку «что это должно быть» (из брифа).
   Вопрос — дословно: «Посмотри скриншот(ы) глазами дизайн-ревьюера: что странного, сломанного,
   недоделанного или нарушающего конвенции продуктовых интерфейсов? Каждая находка: ЧТО — ГДЕ —
   ПОЧЕМУ, серьёзные первыми. Штатные элементы Gravity UI (иконки, коллапс боковой навигации,
   вид стандартных контролов) — не находка. Не выдумывай: лучше 3 настоящие находки, чем 10
   натянутых». Инструмента суб-агентов в среде нет — посмотри сам тем же вопросом (честно
   слабее: глаз автора замылен).
   **Триаж каждого пункта — по проверяемости; впечатление не чинится как впечатление:**
   - Подтверждается независимым замером (DOM-замер, греп кода, кроп скриншота)? Подтвердилось →
     обычная находка: в режиме «после сборки» чини классами (та же дисциплина, максимум
     2 итерации), в standalone — в рекомендации. Опровергнуто замером → отбрось молча.
   - Штатный элемент дизайн-системы (сомнение — сверься с registry)? → отбрось молча.
   - Остальное (полнота, конвенции, вкус — незамеримое) — **не чинить**: топ-3–5 по серьёзности →
     в отчёт блоком «свежим взглядом» (формат блока — скилл `create`, шаг 6), хвост — счётчиком
     «ещё N», раскрывается по запросу пользователя.
6. **Отчёт — два уровня.** Полный разбор пиши в файл `<проект>/gate-out/AUDIT.md`: каждая находка
   с механикой — замеры, file:line, причина, канон-ссылка registry, как чинить. Замер, зависящий
   от ширины вьюпорта (зазоры, переполнения), — только с шириной («118px @1280») и в формулировке
   классом, не константой («колонки фиксированной суммы не отдают излишек — зазор растёт с шириной
   окна»): на другой ширине число другое. В чат — короткая версия: что проверено и НАСКОЛЬКО полно
   (полный/частичный режим — явно); находки и наблюдения списком, **каждый пункт — ОДНО
   предложение «что не так» + в скобках дизайн-причина в 2–5 слов** («неравновесная композиция»,
   «нарушается визуальная иерархия»). Условие места, без которого непонятно, где смотреть
   (ширина экрана, имя колонки), — можно; замеры-доказательства, file:line, имена кода и разбор
   механики — НЕЛЬЗЯ (это уже написано в AUDIT.md, в чате не дублируй). Починку по пунктам не
   расписывай — одна строка на весь список в конце: «могу починить любой пункт — скажи номера».
   Образец: ✓ «Таблица не дотягивается до правого края контейнера, справа пустая полоса
   (неравновесная композиция)» · ✗ «таблица 862px в порту 978px (app.css:34-42) → колонки с
   фиксированным size не отдают излишек — предлагаю width:auto поглотителю». Блок «свежим
   взглядом» (в полном режиме) — тем же форматом пунктов; одна ссылка на AUDIT.md + пути к
   вердикту и скриншотам. Подробности любого пункта — по запросу, из AUDIT.md.

## Чего не делать

- Не редактировать файлы `harness/` и не подгонять проверяемый код «под чек» — находки чинятся по
  гайдам; подозрение на ошибку гейта — опиши, не «чини» здоровый код.
- Static-only-вердикт не выдавать за полную проверку (browser-линии в нём пропущены).
- В standalone-аудите не менять чужой код без явной просьбы.
- Не занимать порт, который пользователь просил для своего предпросмотра, — гейту хватает временного.
- Впечатление свежего взгляда — не основание для правки: чинить только подтверждённое замером;
  неподтверждённое — предложением в отчёте, опровергнутое замером или штатное для дизайн-системы —
  молча отбросить. При конфликте картинки с замером истина — замер.
